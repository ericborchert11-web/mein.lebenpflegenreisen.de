# Cockpit Etappe A — Implementierungsplan

**Goal:** Der Vorstand landet nach dem Login auf `admin-cockpit.html` und sieht dort, was fällig ist: die neuen Vorgänge und Aufgaben aus dem Seed sowie die abgeleiteten Punkte aus den Bestandsmodulen. Etappe A ist **lesend** — bearbeitet wird noch nichts.

**Architecture:** Drei neue board-only Tabellen (`vorgaenge`, `aufgaben`, `vorgang_verlauf`) plus eine reine Lesesicht `v_cockpit_punkte`, die je Quelle eine CTE über eine Bestandstabelle legt. Das Frontend ist eine weitere `admin-*.html` im Hausstil mit einem neuen `LPR.cockpit*`-Abschnitt in `app.js`, gebaut nach dem Muster `foerder*`.

**Tech Stack:** HTML/CSS/Vanilla JS mit `supabase-js`, GitHub Pages, PostgreSQL (Supabase Frankfurt). Tests als Fail-First-SQL im Hausmuster (`raise exception 'TEST BESTANDEN…'`).

**Spec:** `docs/superpowers/specs/2026-09-13-cockpit-design.md`

---

## Kontext, den der Umsetzende kennen muss

**Das Repo ist öffentlich.** `sql/`, `functions/`, `supabase/` und `.superpowers/` stehen in `.gitignore` und werden **nicht** committet. Was dort entsteht, legt der Agent Eric im Chat vor.

**Kein Deploy-Zugang und kein DB-Zugang.** Migrationen führt Eric im SQL-Editor aus. Deshalb steht am Anfang die Vorprüfung `sql/2026-09-13-vorpruefung-cockpit.sql`: **ohne ihr Ergebnis wird keine Sicht geschrieben.** `sql/` reicht nur bis 15.08.2026 zurück; `bookings`, `claims`, `foerder_*`, `einsaetze` und `trips` sind älter und dort nirgends definiert. Geratene Spaltennamen fallen erst beim ersten Aufruf auf.

**Der Supabase-SQL-Editor verträgt nur `$$`**, nie `$name$`. Lange Einfügungen werden gelegentlich um Zeilen gekürzt — erste und letzte Zeile nach dem Einfügen prüfen.

**`create table if not exists` schweigt**, wenn eine gleichnamige Tabelle anders aufgebaut daneben steht. Block B der Vorprüfung beantwortet das für `vorgaenge`, `aufgaben` und `vorgang_verlauf`; bei einem Treffer wird der Plan angepasst, nicht die Migration durchgedrückt.

**Zwei stille Schutztrigger** (`a_profiles_spaltenschutz`, `lpr_clinic_details_protect_status`) setzen unerlaubte Werte ohne Fehlermeldung zurück. Das Cockpit schreibt in keine der beiden Tabellen — aber wer beim Testen ein Profil anfasst, muss den Wert zurücklesen; `row_count` beweist nichts.

**`session.role` heißt im Frontend `'klinik'`, in der Datenbank `'clinic'`.** Häufigste Verwechslung im Projekt.

**`app.js` wird mit `?v…` eingebunden.** Eine neue Seite, die eine neue `LPR`-Funktion ruft, braucht die aktuelle Versionsmarke, sonst bekommt ein warmer Zwischenspeicher die neue Seite mit dem alten Skript.

**`LPR_Layout.init()` nicht vergessen.** `admin-reisen.html` ist im Juli ohne den Aufruf live gegangen und hatte keine Navigation.
